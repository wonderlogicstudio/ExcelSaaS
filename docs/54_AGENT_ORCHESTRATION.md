# WorkbookCare — PL / Builder / Reviewer 운영 계약

## EFFICIENCY-01 — 사용자 승인 운영 우선 규칙 (2026-09-15)

사용자가 작업 범위와 중복 축소를 명시 승인했다. 이 절은 아래의 과거 일괄 검증·역할 인계·자동 상향 지침보다 우선한다. 제품 승인·보안·원본 보존·고정 예상값은 약화하지 않는다. 실제 토큰/요금 상한을 강제하는 런타임 설정이 아니라 에이전트 운영 규칙이다.

| 작업 종류 | 역할과 검증 범위 |
|---|---|
| 질문·문서·운영 설정 | 루트 단독. 필요한 파일만 읽고 변경 파일 diff·형식·참조만 검사. 제품 시험·브라우저·배포·역할 로딩 시연 없음. |
| 국소 UI 수정 | 루트 PL + 빌더 1명 + 최종 리뷰어 1명, 순차 실행. 관련 표적시험, 웹 type/build 1회, 변경된 화면만 데스크톱/모바일 및 관련 키보드 확인. 해당 화면의 고정 예상값이 있으면 실제 화면 대조. |
| 엔진·승인·파일·보안 또는 여러 계층 변경 | 영향을 받는 계약의 통합/음성 시험과 실제 산출물 검증. 전체 회귀는 최종 변경본에서 1회. 해당 영향을 설명할 수 있는 경우만 범위를 넓힌다. |

- 시작 지시는 결과 1개, 허용 영역, 합격조건 최대 3개, 실행할 검사, 재사용할 증거, 종료 조건을 짧게 고정한다. 새 결함은 현재 변경의 회귀이면 고치고, 무관하면 다음 제안으로 기록한다.
- UI만 바뀌고 엔진·승인·납품 경로에 영향이 없으면 기존 Excel/다운로드/재계산 증거의 버전과 불변 근거를 인용한다. 두 수정 기능 전체 납품·725개 값·Excel COM을 습관적으로 재실행하지 않는다. 재사용 증거를 이번 실행 PASS로 표현하지 않는다.
- 같은 소스/설정/입력의 통과 검사는 역할 간 공유한다. PL과 리뷰어는 diff와 실제 로그를 검토하며 같은 시험을 다시 실행하지 않는다. 새 코드, 실패, 구체적인 미해결 위험이 있을 때만 영향 검사 재실행 사유를 적는다. 시작 시 전체 baseline 회귀와 최종 전체 회귀를 중복 실행하지 않는다.
- 리뷰는 최종 1회가 기본이다. 수정 요청 뒤에는 해당 지적과 영향만 재검토한다. 일반 UI/문서는 GPT-5.5 Medium 리뷰, 승인·파일 보존·보안의 복잡한 위험만 Astra High. 빌더 기본 GPT-5.5 Medium, 단순 문구 Low. 현재 대화 모델은 파일 저장으로 바뀌었다고 주장하지 않는다.
- 동일 원인 수정은 최초 시도 뒤 재수정 1회까지만 자동 수행한다. 두 번 실패하면 증거를 보존하고 원인/남은 선택지를 보고한 뒤 사용자 결정 전 추가 빌더·모델 상향·장기 검증을 중단한다. 실패 결과를 완료로 표시하지 않는다.
- 하위 에이전트는 추가 위임 금지. 전체 대화 fork 금지, fork_turns=none과 필요한 경로·작업 요약만 전달. 장기 대기 역할과 중복 PL을 만들지 않는다.
- 최신 milestone/progress의 현재 절과 관련 review만 읽는다. 대형 문서·AX 트리는 필요한 구간만 출력한다. 화면은 행동 뒤 최소 상태 확인, 대표 변경 상태의 스크린샷으로 충분하며 같은 화면을 반복 촬영하지 않는다.
- 결과 상세는 단일 review에 두고 진행 문서는 링크와 짧은 delta만 추가한다. 과거 기록은 보존한다. 측정하지 않은 사용량 절감률을 약속하지 않는다. 필요 검증이 끝나면 추가 탐색 없이 종료한다.


2026-09-15 사용자 승인: 세 역할의 운영 구성과 측정 가능한 편의성 기준. 이번 단위 ID는 `ORCH-01`이다. 제품 기능 개발·화면 변경·배포는 이번 구성 작업에 포함하지 않는다. 이 계약은 기존 코드·검증·D08 PARTIAL 판정을 보존하며, 새 개발 단위의 승인을 만들지 않는다.

## PL이 지킬 서비스 대전제

**Excel을 잘 모르는 고객도 지원되는 문제와 수정 예시를 이해하고, 정확한 변경을 승인한 뒤, 원본과 분리된 수정본 XLSX·변경내역 XLSX·재검증 HTML을 받는다.**

- 핵심 흐름: 업로드 → 탐지 → 지원 수정안과 실제 전후 예시 → 정확한 변경 승인 → 사본 생성 → 같은 검사로 해결 여부 확인 → 세 파일 수령.
- PL은 모든 작업에 “이 변경으로 고객이 어떤 일을 더 쉽게 끝내는가?”를 한 문장으로 답한다. 답이 없거나 핵심 흐름과 무관하면 별도 제안으로 보류한다.
- 먼저 기존 RP01 숫자 타입 정리·RP02 빈 셀 수식 복원을 재사용한다. 탐지·계산·패치·승인·납품 자산을 다시 만들지 않는다. 새 규칙·AI·대시보드·상태 관리 체계 확대는 별도 범위다.
- 무료 진단·위치·근거·CSV·위험 점수와 현재 통합된 결과 UX를 유지한다. 구조/M4의 내부 계약·불확실성·검사 한계는 보존한다. 패턴 후보는 업무 오류 확정이 아니다.
- 전체 요약 → 문제 유형별 묶음 → 필요한 위치·근거 순서. 공통 설명은 유형당 한 번, 개별 셀은 차이만 설명한다. 기술 코드·엔진 상태는 필요한 상세에 둔다.
- 비교/대사는 별도 보고서 상품이다. B를 정답으로 사용하지 않고 원본을 덮어쓰지 않는다. 정밀검증·자동화 안내는 주 흐름을 방해하지 않으며 미구현 기능을 판매 가능으로 표시하지 않는다.
- 대표 예시·확인함·수정 검토 선택·업무 기준 확인·결제는 정확한 변경 승인이 아니다. 전체 변경 접근/필수 공개와 별도 승인, 실행 전 검증, 변경된 조건의 이전 승인 무효화를 유지한다.
- 계산값은 실제 지원 엔진 실행 근거가 있어야 한다. 저장 캐시·희망값·패턴 제안을 계산 결과로 표현하지 않는다. 미지원·불일치·검증 불가는 설명하고 안전하게 멈춘다.

## 역할과 자동 인계

루트 대화가 **PL 겸 오케스트레이터**다. 사용자는 이 대화에 목표·수정 의견·승인을 전달한다. PL이 빌더/리뷰어에게 작업과 결과를 전달하며 사용자가 명령문을 복사할 필요가 없도록 한다. 독립 `pl` 에이전트는 PL 검토를 위임할 때만 쓰고 같은 PL을 중복 상시 실행하지 않는다.

| 역할 | 산출물과 책임 | 수정 범위 |
|---|---|---|
| PL | 사용자 목표·승인 근거·한 단위 작업지시, 인계, 검토 결과 통합, 상태와 다음 제안 | 루트는 운영/진행 기록만 갱신; 제품 소스 수정 금지. 위임된 pl은 읽기 전용으로 보고 |
| Builder | 재사용 조사, 승인 파일 구현, 표적시험→원인 수정→재시험→관련 통합검증, 실제 산출물 | 작업지시의 파일/영역만 수정. 예상값·승인 범위·완료 기준을 자의적으로 바꾸지 않음 |
| Reviewer | 빌더와 분리된 코드/증거 확인, 재현·반례, 실제 예상/결과 대조, PASS/CHANGES_REQUIRED/BLOCKED 판정 | 제품 소스·정답표 수정 금지. 쓰기가 필요한 시험은 허용된 임시/증거 경로만 사용하거나 PL에 요청 |

기본 동시 구성은 루트 PL + 최대 두 하위 에이전트다. 구현 전 작업지시, 구현 후 검증은 순차 의존 관계다. 독립 읽기 조사만 유용할 때 병렬화한다. 제품 소스의 동시 작성자는 한 빌더로 제한하고 하위 에이전트가 추가 역할을 무한 생성하지 않는다. 모델·추론 강도는 아래 ORCH-02 배정 정책을 따른다. 별도 지정하지 않은 일반 하위 작업의 기본값은 GPT-5.5 Medium이다.

프로젝트 설정은 `.codex/config.toml`, 역할은 `.codex/agents/{pl,builder,reviewer}.toml`에 둔다. 모델/권한의 전역 설정은 변경하지 않는다. PL/리뷰어의 `read-only`, 빌더의 `workspace-write`는 요청하는 기본 sandbox이며 부모의 실행 중 권한 설정이 우선할 수 있다. 파일별 허용 목록과 외부 작업 금지는 운영 지침이고 OS 접근제어로 검증된 것으로 주장하지 않는다. 실제 강제성이 필요하면 격리 작업공간과 도구 권한을 별도 검증한다.

현재 세션처럼 역할 이름 선택 도구 없이 `task_name`과 메시지로 위임하는 환경에서는 PL이 해당 TOML의 지침을 직접 읽어 작업 메시지에 적용한다. 그 실행은 **역할 지침 기반 위임**으로 기록하며 네이티브 역할 로드나 read-only 강제 적용 성공으로 표시하지 않는다. 프로젝트 기본 자동 적용은 ExcelSaaS를 작업 루트로 열 때 확인한다. 다른 프로젝트의 전역 설정을 건드리지 않는다.

## 모델 배정 — ORCH-02 (2026-09-15 승인)

사용자가 역할·난이도별 모델 분리를 승인했다. 기존 제품 대전제와 검증 수준은 유지하며, 모델을 낮췄다는 이유로 합격조건을 줄이지 않는다.

| 역할/작업 | 기본 배정 | 상향/하향 기준 |
|---|---|---|
| PL | GPT-6 Astra Medium | 상충하는 제품 요구·설계/안전 경계 판단은 Astra High로 한정 검토 |
| Builder | GPT-5.5 Medium | 문구/간격 등 명확한 국소 변경은 Low. 수식/파일 보존/승인 상태/재검증 연계는 High |
| Reviewer | GPT-6 Astra High | 최종 결과·승인/보존·회귀를 집중 검토. 사소한 편집마다 전체 재검토하지 않음 |

- 동일 원인 수정이 두 차례 실패하거나 영향 범위를 설명할 수 없으면 실패 증거를 모아 PL에게 반환한다. 필요할 때 해당 난제만 Astra High로 위임하고 해결 후 기본값으로 복귀한다. `xhigh/max/ultra`를 자동 선택하지 않는다.
- 현재 위임 도구는 Spark를 지원하지 않는다. 단순 수정은 GPT-5.5 Low를 사용하며 Spark를 사용했다고 보고하지 않는다. 다른 실행 환경에서 Spark가 실제 선택 가능한지 확인하기 전에는 배정하지 않는다. 플러그인이나 새로운 유료 자원을 설치하지 않는다.
- `.codex/config.toml`은 새 프로젝트 실행의 PL 기본 모델/강도와 일반 하위 작업 기본값을 지정한다. 역할 TOML은 각 역할의 기본 모델/강도를 명시한다. 기존 세션의 실제 모델은 설정 파일 저장만으로 바뀌지 않으며, 실행 중 UI/런타임 선택이 우선할 수 있다.
- 역할 TOML의 고정 모델/강도가 spawn 인자보다 우선할 수 있다. 비기본 Low/High 작업은 **고정 역할 설정을 적용하지 않는 일반 위임**에 해당 역할의 지침과 명시적 model/effort를 전달한다. 현재 도구에서는 `fork_turns="none"`과 구체적 작업지시로 시작한다. 일반 위임 또는 모델 선택이 불가능하면 요청/실제 선택 차이를 보고하고 확인된 기본값을 사용하며, 적용 성공을 꾸미지 않는다.
- 인계에는 작업 ID·승인 범위·역할·난이도·요청 model/effort·선정 이유·필요한 파일/검증 근거만 전달한다. 전체 대화 복제와 저장소 전체 재탐색을 기본으로 하지 않는다. 제공되는 실행 메타데이터로 실제 모델을 확인할 수 있으면 기록하고, 확인 불가하면 요청값과 구분한다.
- 모델 선택을 시험하기 위한 불필요한 대화/벤치마크를 추가하지 않는다. 실제 승인 작업에서 사용량·재시도·통과 결과를 관찰하며, 토큰/구독 한도 절감률을 사전에 보장하지 않는다. 설정 검증과 제품/Excel/사용성 검증은 별개다.

## 승인과 상태

`PL 작업지시 → 사용자 승인 → 빌더 구현·시험 → 리뷰어 검증 → PL 결과 보고 → 사용자 다음 단위 승인`

- 현재 사용자 요청에 이미 승인된 결과·범위가 있으면 승인 근거로 기록하고 같은 허가를 다시 묻지 않는다. 새로운 범위는 구현 전에 작업지시와 합격조건을 먼저 제시한다. “승인 대기”는 답변/승인 자체가 아니다.
- 승인 범위 안의 원인 수정·재시험은 자동 반복한다. 새 제품 동작·지원 범위·정답표/waiver·보안 조건 변경은 PL에 반환한다. 제품 범위 변경에는 사용자 승인이 필요하고, 정답표 결함은 실패와 독립 근거를 보존해 별도 결정을 받는다.
- 검토 실패는 빌더에게 재현 방법과 함께 반환한다. 동일 원인으로 두 차례 수정 후에도 실패하면 원인·시도·남은 선택지를 PL에 보고해 반복 방식을 재검토한다. 이 규칙은 자동 성공 처리나 무조건 작업 중단이 아니다.
- 검토 PASS는 엔지니어링 판정이다. 사용자 수용·상용 readiness·개발 승인·고객 변경 승인·배포 승인은 서로 별개다. 다음 단위를 자동 승인하지 않는다.
- 기존 Access 보호 베타의 명시적 배포 승인은 유지한다. 승인된 제품 변경의 검증에 필요할 때만 기존 배포 절차를 따른다. 이번 운영 설정은 배포 대상이 아니다. 원격 push·실고객 자료·실결제/환불·가격 확정·새 유료 자원·익명 공개·사용자 초대는 별도 명시 승인 없이 실행하지 않는다.
- 상태가 바뀔 때 `PL [오더 작성/승인 대기/조정 중/결과 보고]`, `빌더 [대기/구현 중/수정 중/시험 완료]`, `리뷰어 [대기/검토 중/수정 필요/검증 완료/차단]`와 실제 근거·다음 행동을 보고한다. 실행하지 않은 역할을 “작업 중”으로 표시하거나 추정 진행률을 쓰지 않는다.
- 지속 상태는 `docs/delivery-v3_2/delivery-progress.json`의 해당 작업 delta, 상세 근거는 review에 저장한다. 기존 기록은 보존하고 현재 상태를 앞에 짧게 추가한다. 대화 초기화 후에는 최신 milestone/progress/관련 review부터 재개한다.

## 편의성 예산 — 초기 설계 목표, 현재 달성 결과 아님

AI의 자체 판단으로 “편리하다”를 PASS 처리하지 않는다. 아래 수치는 업계 기준이 아닌 초기 제품 목표이며 실제 측정값은 별도다. 이번 설정에서는 모두 `NOT_MEASURED`, 인간 수용 시험은 `NOT_RUN`이다.

| 지표 | 초기 목표 | 집계 기준 |
|---|---:|---|
| 주요 진행 단계 | 4 이하 | 무료 진단 / 수정안 확인 / 정확한 변경 승인 / 결과 받기. 숨긴 하위 필수 절차도 별도 기록 |
| 필수 앱 활성화 | 10회 이하 | 빈 작업에서 파일 선택기 호출부터 세 산출물 실제 수령까지. RP01/RP02의 각각 한 제안 그룹·기본 전체 범위·의견 없음 경로 |
| 필수 셀 주소·수식 직접 입력 | 0회 | 대표 지원 경로에서 시트·발견 위치·원본 기준 수식을 선택할 수 있어야 함 |
| 같은 정보 재입력 | 0회 | 동일 유효 작업 안에서 이미 제공한 정보 재요구. 새 파일/만료/업무 조건 변경은 따로 기록 |
| 현재 다음 행동을 강조하는 CTA | 1개 | 각 상태에서 다음 주 행동 하나. 취소·뒤로·상세·산출물별 링크는 목적을 구분한 보조 행동 가능 |
| 고객이 해야 할 업무 판단 | 항목과 횟수 공개 | 금액/개수/번호·기준 계산 선택 등. 횟수를 줄이려고 AI가 업무 정답을 대신 확정하지 않음 |

**측정에서 제외해 숨기지 않는다:** 필수 펼치기, 업무 확인, 업로드 동의, 정확한 승인, 실행, 세 개 다운로드는 앱 활성화에 포함한다. 드롭다운 선택은 의미 있는 선택 횟수와 실제 열기/선택 클릭을 모두 기록하고 10회 예산에는 실제 활성화를 센다. 키보드는 동일 컨트롤 활성화로 비교하되 포커스 이동 키 횟수는 별도 기록한다. OS 파일 선택 내부·Access 로그인·스크롤·선택적 상세·전체 대기 시간은 별도 집계하고 총 사용자 부담에 함께 표시한다. 사전 주입 상태·API 직접 호출로 UI 단계를 건너뛰어 클릭 예산을 검증하지 않는다.

부분 선택·여러 그룹/시트·의견 입력·재시도·정상/미지원/만료/조건 변경은 확장 시나리오로 추가 행동과 원인을 보고한다. 정상/미지원 파일을 억지로 수정 흐름에 통과시키지 않는다. 숨겨진 비용·재업로드·되돌아감·도움 요청·다른 화면으로 이동도 관찰한다. 클릭 목표가 안전한 승인과 충돌하면 초과 실측과 대안을 PL에 제출하며 승인/검증을 생략하거나 목표를 몰래 올리지 않는다.

숫자만으로 고객 이해를 확정하지 않는다. 후속 승인된 사용성 시험에서는 합성 파일로 고객이 도움 없이 완료하고 “무슨 문제인지 / 무엇이 바뀌는지 / 원본과 결과가 어디 있는지”를 설명하는지 확인한다. 첫 소규모 시험 목표는 5명 중 4명이며 모집·초대는 이번 승인에 포함되지 않는다. 소수 시험 통과를 시장 전체의 편의성 증명으로 확대하지 않는다.

## 인계와 검증 증거

작업지시는 한 개만 유지하며 다음 필드를 포함한다. 단순 질문에는 에이전트를 띄우거나 작업지시를 만들 필요가 없다.

```text
ID / 현재 상태 / 사용자 승인 근거
고객이 완료할 행동 한 문장
현재 구현·재사용할 코드 / 부족한 acceptance
허용 파일 또는 영역 / 제외 범위 / 단일 작성자
시나리오·고정 입력/예상값·정상/미지원 반례
UI 단계/활성화/입력 예산 또는 해당 없음
표적시험·관련 통합검증·화면/다운로드/Excel 검사 계획
실행 권한·기존 승인 / 종료 조건 / 다음 단위 NOT_APPROVED
```

빌더·리뷰어는 실제 변경/재사용, 명령·exit code, 입력/버전, 예상값 대비 실제값, 화면/다운로드/검사 증거, 실패 원인·수정·재시험, 미실행 항목을 반환한다. 단순 스크립트 존재·예시 fixture·계약 모형·읽기 검토를 실제 제품/Excel/공식 PG/사람의 이해 검증으로 세지 않는다.

제품 변경의 핵심 합격조건은 고정 합성 XLSX → 실제 탐지 → 지원 여부 → 정확한 승인 → 별도 수정/변경내역/보고서 → 원본/비대상 보존 → **처음 후보를 만든 동일 검사로 수정본을 재검사해 해당 후보 해결 확인**이다. 정적 재검사 통과를 M4 재검사로 대신 보고하지 않는다. 후보 해소는 업무 정답 보증도 아니다. 남은 후보·미지원·새 위험도 기록한다.

화면이 변경되거나 사용자 흐름의 예상값이 있으면 기존 보호 베타에서 데스크톱/모바일을 실제 확인하고 예상값을 대조한다. 키보드 경로도 별도 확인한다. 수정본은 실제 다운로드하고 기존 합성 expected 및 필요한 Excel 확인을 수행한다. UI 변경이 없는 운영 설정은 구성 파싱·로딩·역할 인계·권한 한계·기존 파일 보존으로 검증하며 제품 회귀를 실행했다고 보고하지 않는다.

Ponytail의 재사용·표준 기능 우선·최소 변경 원칙을 빌더와 리뷰어에 적용한다. 플러그인 설치나 전체 저장소 정리 작업은 이번 범위가 아니다. 검증·오류 처리·보안·접근성·Excel 보존을 코드 감소를 위해 제거하지 않는다.
