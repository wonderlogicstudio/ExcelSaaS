# Accepted decisions

| ID | Decision | Rationale | Status |
|---|---|---|---|
| D-001 | Web-first, not native mobile | Workbook handling, search acquisition, and payment iteration are better on the web | Accepted |
| D-002 | React/TypeScript frontend | Strong ecosystem, Codex support, and future Cloudflare deployment | Accepted |
| D-003 | Python/FastAPI backend | Excel processing ecosystem and straightforward container deployment | Accepted |
| D-004 | Cloudflare edge/R2 + Google Cloud Run target | Low idle cost with conventional Python compute | Accepted |
| D-005 | Deterministic scan before AI | Lower cost, higher reproducibility, better privacy | Accepted |
| D-006 | Per-file quote before payment | File complexity varies and transparent scope reduces disputes | Accepted |
| D-007 | No original overwrite | Safety, trust, and rollback | Accepted |
| D-008 | Audit-only for macro/high-fidelity-risk files initially | Prevent macro execution and OOXML fidelity loss | Accepted |
| D-009 | No fake social proof or performance claims | Trust must be evidence-based | Accepted |
| D-010 | Human milestone gate | Prevent token waste, scope drift, and cascading rework | Accepted |
| D-011 | One approved milestone per Codex goal | Long enough for autonomy, small enough for review | Accepted |
| D-012 | Working name `WorkbookCare` only | Final domain/trademark work remains | Temporary |
| D-013 | No third-party analytics in initial test | Minimize privacy and implementation overhead | Accepted |
| D-014 | Subscription deferred | Initial use is episodic and per-file willingness to pay must be proven first | Accepted |
| D-015 | Evidence-grade UI instead of confidence percentages | Current confidence values are not calibrated statistical accuracy | Accepted |
| D-016 | Structural risk shown as a label first | Current weights are an empirical prioritization aid, not an error or loss probability | Accepted |
| D-017 | `INFORMATION_ONLY` is a first-class repairability class | Informational findings must not imply a modification is needed | Accepted |
| D-018 | Recommendation engine and service catalog are separate | Findings recommend technical next checks; planned deliverables, status, and price ranges need independent product control | Accepted |
| D-019 | Scanner-generated fixture is the sample-result source of truth | Prevents frontend sample claims from drifting beyond the current static scanner | Accepted |
| D-020 | M2.5 is a no-commerce, no-repair boundary | Price ranges remain hypotheses; payment, request, approval, and repair require later milestones | Accepted |
| D-021 | Repair-readiness is derived, not a new diagnostic rule | Existing repair classes can describe a future safe path without claiming a current automatic repair capability | Accepted |
| D-022 | Free results show a resolution path, not a purchase action | The funnel should explain why precision verification and approval matter before repair is implemented | Accepted |
| D-023 | Re-validation starts with the same open browser session | It proves the direct-edit loop without DB, account history, server file retention, or a new privacy surface | Accepted |
| D-024 | Use “이번 재검사에서 더 이상 탐지되지 않음,” not “해결됨” | Static rules cannot prove business correctness, recalculated values, or a complete repair | Accepted |
| D-025 | Free results show every current Finding and its deterministic manual guide | Free value is evidence, location, direct checking, and re-scan—not a warning paywall | Accepted |
| D-026 | Finding comparison uses a value-free rule-and-location key | It enables a minimal comparison while avoiding formula or cell-value persistence; renamed sheets and moved cells remain documented limits | Accepted |
| D-027 | Browser-generated UTF-8 BOM CSV is the first export format | It is useful to Korean Excel users without PDF libraries or server-side result storage | Accepted |
| D-028 | M3 tests comprehension and conversion intent, not Repair delivery | Repair implementation remains an M7 approval-gated scope | Accepted |
| D-029 | Use one sticky-header scroll offset for every anchor and CTA | CSS `scroll-padding-top` keeps native hash navigation and programmatic section scrolling consistently readable below the fixed header | Accepted |
| D-030 | Header labels must match distinct titled destinations | Free diagnosis, precision verification, automation consultation, file-processing principles, and FAQ are different user intents; planned services receive dedicated explanatory sections rather than card-level anchors | Accepted |
| D-031 | Use progressive disclosure for Finding evidence | The first decision needs identity and severity, while detailed evidence and local status must remain available on demand without duplicating every Finding | Accepted |
| D-032 | M3 uses an 8-person staged qualitative protocol | Round 1 has 3 exploratory sessions and Round 2 has 5 confirmation sessions; this supersedes the older 10-person M3 pass threshold but does not claim market representativeness | Accepted |
| D-033 | Identify the M3 baseline by scanner assets when Git metadata is unavailable | This workspace has no Git repository, so the test date, scanner/rule-set versions, synthetic workbook names, fixtures, and verification command provide the reproducible baseline | Accepted |
| D-034 | No product change before actual Round 1 observations | Testing the verified M2.5 compact Finding UI avoids conflating preparation with an unvalidated redesign; P0/repeated P1 changes require explicit approval | Accepted |
| D-035 | Test review-marked-copy value before implementing it | A separate, navigable review copy may reduce Excel location-finding friction, but it must remain a future hypothesis until M3 confirms the need and a later fidelity gate proves it safe | Accepted as hypothesis |
| D-036 | Defer external M3 and M3.5 validation until hosted beta | Internal review is not a substitute for user understanding, market, pricing, or conversion evidence; M4-A stays a narrow reversible technical investment | Accepted |
| D-037 | Limit M4-A to two conservative formula-pattern candidate classes | Dominant-pattern outliers and formula gaps/constants provide a focused quality gate; unsupported syntax and normal structural exceptions are skipped rather than guessed | Accepted |
| D-038 | Feedback capture is local, default-off, and value-free | An interface and local repository prepare later research without a feedback API, tracking, file data, locations, formulas, or server storage | Accepted |
| D-039 | M4-B requires a labelled formula-audit quality gate | M4-A synthetic unit tests alone cannot establish normal-exception handling, reproducibility, explainability, or performance readiness | Accepted |
| D-040 | Formula-audit metrics are synthetic-corpus metrics, not accuracy claims | Fixed labels make regressions measurable without claiming business-formula correctness or general real-world precision | Accepted |
| D-041 | Local formula-audit review output is de-identified | Finding keys include locations, so local aggregate outputs must exclude filenames, sheet/cell locations, keys, values, and formula text | Accepted |
| D-042 | A relative M4 performance threshold requires human review | A 2× M4-to-baseline threshold exposes material added work even when absolute time remains small; an exceeded threshold produces Conditional Go, never automatic exposure | Accepted |
| D-043 | Detection rule code and evidence subtype are separate | A single candidate rule may explain function, sheet, relative/absolute-reference, or range drift without inflating coverage or priority counts | Accepted |
| D-044 | Engine state, quality-gate state, and exposure state are independent | `PROTOTYPE`, `CONDITIONAL`, and `INTERNAL_ONLY` describe different decisions; no one value authorizes another | Accepted |
| D-045 | Every future detection candidate has a release-gate contract | Target/normal/unsupported corpus, accuracy or clean-case threshold, performance, privacy-safe evidence, Excel check guidance, and a fail-closed exposure rule are required before release | Accepted |
| D-046 | Blueprint recommendations do not approve implementation | The recommended silent-error batch sets research order only; each rule needs a separately approved milestone and its own quality gate | Accepted |
| D-047 | M4 candidates must be isolated from baseline diagnosis output | An optional audit envelope prevents internal pattern candidates from changing free findings, risk, quote, repair counts, CSV, or default Results | Accepted as M4-B contract |
| D-048 | Audit execution outcome is separate from rule status | `ABSTAINED`, skipped, unsupported, and failed outcomes describe one run and emit no candidate; they do not change lifecycle, quality, or exposure status | Accepted |
| D-049 | M4-C supports value-free literal categories, not literal values | Numeric, text, logical, and error operands in supported expression contexts may participate in normalized pattern comparison so common business formulas can be compared; their actual values remain absent from evidence, output, logs, and feedback | Accepted |
| D-049 | Internal beta access requires a server-side fail-closed gate | A public-client flag or hidden UI cannot protect a beta without accounts; public environments expose no M4 choice or endpoint | Accepted as M4-B contract |
| D-050 | Current M4 internal-beta eligibility is bounded by verified workload | Require complete baseline scan and 1–30,000 formula cells; retain both absolute added time and relative ratio, and show only indeterminate progress with the synchronous API | Accepted as M4-B contract |
| D-051 | Manual M4 review is a blank synthetic-only checklist | Human observation must be recorded separately from automatic results; no customer file, personal data, or invented completion is allowed | Accepted |
| D-052 | Independent formula-audit evidence starts with a separate synthetic holdout | Existing 40-case results are development-corpus metrics; any non-sensitive real-file review needs separate privacy, retention, and access approval | Accepted |
| D-053 | M4-B uses a separate `POST /v1/formula-audits` response, not an optional field on the free scan | Separate request/response keeps current API compatibility and prevents optional candidates from changing the baseline result, risk, quote, repair totals, or CSV | Implemented |
| D-054 | M4-B access requires server gates plus a non-security browser visibility flag | `APP_ENV=development|internal_beta` and `FORMULA_PATTERN_AUDIT_ENABLED=true` fail closed at the API; `VITE_FORMULA_AUDIT_INTERNAL_BETA_ENABLED` only controls whether the internal UI is rendered | Implemented |
| D-055 | M4-B feedback is category-only and local | The UI stores only helpful / possible-false-positive / explanation-insufficient category records in browser localStorage; free text could expose workbook data and is excluded | Implemented |
| D-056 | M4 candidates remain isolated even when the server feature flag is enabled | `scan_workbook()` no longer calls formula-pattern detection. The audit endpoint owns the only candidate path and regression tests compare baseline contracts before/after audit | Implemented |
| D-057 | Internal-beta startup must fail instead of silently reusing a default local server | A separate M4 audit is invisible in safe default mode. The local launcher therefore sets both gates in the spawned API/browser processes and stops before launch when the normal ports are already occupied | Implemented |
| D-058 | Summary-row markers apply only to static row labels | A formula can legitimately reference a sheet whose name includes `총계`, `total`, or `adjustment`; formula source text is not evidence that its own row is a subtotal/manual row | Implemented in M4-C remediation |
| D-059 | Immutable validation labels must be internally consistent | A cell cannot be both an expected target and a normal exception. The combined M4-C evaluator fails closed on target/normal overlaps and records the exact conflict without changing source labels | Accepted; M4-C completion blocked pending corrected source fixture |
| D-060 | Product owner may accept only a named fixture waiver | `M4C-2026-09-02-source-label-conflict` accepts exactly two reviewed additional-pack target/normal overlaps. The evaluator preserves labels, reports the waiver, and continues to fail on every other conflict or gate | Accepted for M4-C baseline |
| D-061 | Hosted-beta feedback remains category-only | Free text can contain workbook content or personal data. M4-D removes UI memo input and strips legacy local memo values; no feedback API, database, or telemetry is added | Implemented |
| D-062 | M4 capacity limits must fail safely, not truncate candidates | Sheet/formula/candidate limits are controlled through settings. An audit emits a named skip result instead of a partial candidate list, while the base diagnosis stays unchanged | Implemented in RC |
| D-063 | M4-C source-label waiver is a release-record exception, not a fixture change | The owner accepted exactly two contradictory target/normal labels after the engine met every other gate. The immutable source labels and checksums remain unchanged; a corrected upstream pack is still preferred | Accepted for local RC only |
| D-064 | Hosted beta is same-origin control plane, not a public Cloud Run API | Browser traffic terminates at an Access-protected Worker route; R2 stays private and Cloud Run needs authenticated invocation. H1 documents and prepares this boundary without deploying it | Accepted for H1 |
| D-065 | Hosted environment configuration must fail closed before service startup | `hosted_beta` and `production` accept only declared environments and exact HTTPS CORS origins; wildcard and local origins fail validation. CORS accepts a JSON array or comma-separated environment string through one parser | Implemented and locally verified in H1 |
| D-066 | Hosted observability may contain only an explicit safe allowlist | Application events reject workbook content, locations, object URLs, identities, and free text; unexpected failures return a generic safe code rather than exception text | Implemented and locally verified in H1 |
