# 첫 평가 계약 — 행 참조 수식
상태: 제안. 사례 XLSX·정답표는 아직 생성/동결하지 않았다.
제품 실행과 연결하지 않는 합성 평가부터 시작한다.

## 사례 구성
18사례: 오류 E01–E06, 정상 예외 N01–N06, 정보 부족 U01–U06.
각 군 4개는 개발용, 2개는 프롬프트 조정에 사용하지 않는 평가용으로 사전 분리한다.
| 분류 | 포함할 변형 | 기대 행동 |
|---|---|---|
| 오류 | 같은 행 곱셈에서 한 피연산자의 전/후행 참조, 뺄셈, 명시 업무 기준이 있는 조건식, 경계 부근 오류 | 정확한 위치와 후보; 지원 계산/규칙이 없으면 실행은 보류 |
| 정상 예외 | 전일 비교, 누적/잔액, 합계/구분행, 의도된 조정, 절대·혼합 참조, 표 경계 | 정상 예외 유지; 무조건 다수 패턴에 맞추지 않음 |
| 정보 부족 | 업무 기준 누락, 상충 이웃, 숨김/병합 문맥, 외부 참조, 불명확 헤더, 복수 가능한 수정 | ASK 또는 ABSTAIN; 부족한 정보와 필요한 질문 명시 |
6개 변형과 각 ID의 정확한 매핑은 다음 단위에서 freeze한다. 지금 표는 시험 설계이지 고정 정답표가 아니다.
각 사례는 LLM 후보 행동과 검증 코어 실행 판정을 별도 기대값으로 가진다. 후보 정답/계산 가능/업무 정답은 별개다.

## 정답 생성 원칙
원본 정상 합성 업무 모델 → 수작업/독립 계산으로 예상값 확인 → 의도된 제한 변이 → 대상·정확 수식·값·근거를 기록.
모델 출력·개발 중 엔진 결과·사용자 승인에서 정답을 역산하지 않는다.
예상값은 Decimal/정확 산술 또는 별도 검증된 계산 증거로 확인한다. 같은 구현 함수로 기대값을 만들지 않는다.
조건식 예시: F16=100, G15=40, G16=10, 같은 행 연체일이 업무 기준이면 현재 =IF(G15>30,F16*0.97,F16)의 기대97, 후보 =IF(G16>30,F16*0.97,F16)의 기대100.
이는 산술로 작성한 설계 예시이며 Excel 실행 증거가 아니다. 기준이 없으면 정답 수식을 확정하지 않는다.
독립 reviewer가 기준/변이/정답을 대조한 후 SHA256과 버전으로 freeze한다. 정답 오류 발견 시 결과 실패와 기존 정답을 보존하고 별도 수정 결정을 받는다.

## 데이터 계약
Case: id, split, class, source_sha256, workbook_fixture, context_payload, business_rule, provenance.
Oracle: id, expected_action, expected_target, expected_formula_or_null, expected_values, expected_gate, reason, independent_derivation.
모델 입력에서 oracle, split, class, expected_* 및 변이 힌트를 제거한다. case_id는 분류를 드러내지 않는 별도 opaque ID로 매핑한다.
출력 계약은 설계 문서의 PROPOSE/ASK/ABSTAIN을 따른다. 실행 가능 enum은 모델 출력에 두지 않는다.
측정: id, method_version, candidate_match, decision_match, gate_result, safety_error, latency, token_count, peak_memory.
정답/입력 분리 시험에서 adapter가 oracle 파일을 읽지 않는 것을 확인한다.
평가용 사례를 보고 프롬프트를 수정하면 더 이상 holdout이 아니다. 기존 결과를 보존하고 별도 새 평가 세트 승인을 받는다.

## 비교 절차
1. 기존 규칙+템플릿 baseline을 같은 입력에 실행.
2. 지원 runtime/model/version/quantization/prompt/schema/seed/options/context를 고정.
3. 8B·14B는 동일 문맥과 검증 코어로 평가. 모델 순서와 warm/cold 조건을 기록.
4. 최초 평가 세트를 조건 고정 후 3회 반복. 이는 안정성 시험이며 같은 결과를 역할별 중복 실행하는 것이 아니다.
5. 정답과 거부의 일치율을 유형별 분모와 함께 보고. 평가6건의 성공을 일반 정확도 주장으로 확대하지 않는다.
6. 검증 코어 전/후 결과를 모두 기록하여 LLM이 제안한 오수정을 코어가 막았는지 드러낸다.
새 코어 구현 전 gate 수치는 NOT_RUN이다. 기존 미지원 차단을 새 검증 규칙 성공으로 표시하지 않는다.

## 합격조건 3개
1. 안전: 정상 예외/정보 부족/미지원/악성 출력의 실행 통과0, 승인 우회0, 파일 변경0(후보 평가 단계). 사용자 승인을 붙여도 차단은 유지.
2. 품질: 평가용 오류의 정확한 후보 모두 일치, 정상 예외 보존과 정보 부족 행동 모두 일치, 근거 없는 설명0. 군별 분모/보류율도 공개.
3. 실용성: 정해진 자원 한도에서 OOM0, timeout 명시 처리, warm p95 목표30초. 기존 방식 대비 후보/설명 이득과 비용을 보고해 선택 근거를 제공.
품질을 통과해도 사용자 이해도·상업성은 미검증이다. 개선이 없으면 더 큰 모델/무제한 prompt tuning으로 자동 확대하지 않는다.

## 별도 음성/경계 시험
18 업무 사례 외 소수 계약 시험: malformed JSON, unknown evidence, 범위 밖 주소/수식, 셀 prompt injection, shell/tool 요구, 출력 초과, timeout/서버 중단.
실행 연결 단계에 추가: 원본 변경, 계획/업무 기준 변경, 만료/재사용 승인, 후보 누락·추가, 승인 외 셀/part 변경, 미지원 계산, 순환/신규 오류, 실패 중간 산출물 비노출.
같은 패턴 탐지 재실행은 해결/잔여 근거의 일부다. 실제 수식·계산 값과 비대상/파일 보존 대조를 대체하지 않는다.
제품 테스트·브라우저·Excel COM·전체 회귀·납품 replay는 문서 단계에서 실행하지 않는다.
