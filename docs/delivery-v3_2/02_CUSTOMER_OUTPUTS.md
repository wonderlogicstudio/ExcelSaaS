# 고객이 결제 후 받는 결과물

## 승인 기반 수정 패키지

성공적으로 승인된 작업에서 고객은 다음 세 가지를 **같은 가격의 한 패키지**로 받는다. 수정본이 없는데 보고서만 주고 수정 상품을 성공 납품했다고 처리하지 않는다.

|필수 파일|내용|고객이 할 수 있는 일|
|---|---|---|
|`workbookcare_repaired_<job>.xlsx`|업로드 원본과 분리된 사본. 승인한 셀 변경 및 명세에 포함된 계산 캐시 갱신만 반영|Excel에서 열고 실제 업무 파일로 사용할지 검토|
|`changes_<job>.xlsx`|변경 셀, 이전/이후 타입·값·수식, 변경 이유, 승인 plan 버전, 기대 영향, 제외 항목|무엇이 바뀌었는지 추적|
|`verification_<job>.html`|원본 보존, 승인 외 변경 점검, 정적/계산/업무 검증 범위, 전후 차이, 잔여/미지원/실패, 도구·버전|검증된 범위와 추가 확인할 부분 판단|

`manifest.json`은 보조 파일이다. 상품·작업·원본/수정본 SHA-256·plan hash·엔진/프로필 버전·파일 목록·생성/만료 시각을 결합한다. 각 파일 개별 다운로드와 ZIP 묶음 다운로드를 제공할 수 있다. ZIP은 동일한 READY 파일만 묶는다.

변경내역의 수식·셀 값은 **고객 전용 비공개 산출물**이다. 이를 운영 로그나 피드백에 저장하지 않는다. ‘원문을 로그에 남기지 않는다’는 원칙을 오해해서 고객의 변경내역도 지워 버리지 않는다.

## 수정 패키지의 성공 조건

- 사용자가 승인한 현재 plan과 실제 수정된 파일이 일치한다.
- 원본 bytes의 hash는 변하지 않는다.
- 필수 세 파일이 모두 생성되고 상호 일치·권한·검증을 통과한다.
- 필요한 계산 검증은 실제 수행했다. ‘Excel에서 열면 계산될 것’은 후검증 완료가 아니다.
- 수정 대상 0개, 전부 거부, 계산 실패, 파일 보존 실패는 수정본 납품 성공이 아니다.
- 신규 입력·새 정책·계획 변경에는 기존 승인을 재사용하지 않는다.

고객 화면의 완료 문구는 ‘승인한 2개 변경의 수정본과 검증 보고서가 준비되었습니다’처럼 범위를 표시한다. ‘파일 전체 오류가 모두 해결되었습니다’라고 쓰지 않는다.

## 두 파일 비교 상품

`comparison_report_<job>.xlsx`와 `comparison_verification_<job>.html`을 받는다. 웹의 분류·원천 행·금액·미상 값과 파일이 일치해야 한다. 원본을 변경하지 않으며 **수정본·정답표·손실확정 보고서가 아니다**. 비교 상품 결제권으로 수정 API를 호출할 수 없다.

## 미지원·실패·취소의 결과

|상황|제공/처리|금지|
|---|---|---|
|결제 전 지원 불가|이유·준비할 자료·가능한 경로 안내; 결제 차단|수정할 수 있는 것처럼 선결제|
|결제 후 정확한 계획 준비|전체 전후 변경과 영향 확인; 별도 승인 대기|결제 즉시 원본 변경|
|고객이 모든 변경 거부|작업 미실행; 공개된 취소/환불 절차|빈 수정본으로 정상 납품|
|후검증/보존 실패|출력 격리; 동일 권리 재시도 또는 보상|미검증 파일을 성공본으로 다운로드|
|보고서만 생성됨|패키지 미완료; 복구/보상|수정 상품 완료 상태|
|성공 후 브라우저 종료|본인 주문으로 재접속·정해진 기간 재다운로드|같은 파일을 받으려면 다시 결제|
|보관 만료|만료 안내; 동의된 재생성 또는 보상 정책|입력/결과를 무기한 보관|

## 설명용 산출물

`examples/repair_delivery/`에는 가상 매출파일의 C7 형식 변환과 E8 누락 수식 복원을 보여주는 샘플이 있다. 이 파일들은 설명용으로 만든 것이며 WorkbookCare 제품 엔진·PG·승인 서버를 실행한 결과가 아니다. 실제 제품 수용시험에서는 앱을 통해 같은 논리의 파일을 새로 생성하고 검증해야 한다.
