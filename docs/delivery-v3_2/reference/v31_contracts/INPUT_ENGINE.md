# 값 기반 두 자료 비교 계약

## 1. 형식과 실제 제한

제품 profile은 `TWO_LEDGER_EXACT_KEY_KRW_V1`이다. XLSX 선택 표 한 개/파일 또는 UTF-8 CSV를 두 원천 A/B로 읽는다. 파일당 10 MiB, 합계 20 MiB를 넘기지 않는다. multipart 부가 크기는 별도 작은 여유 상한을 두며 헤더 Content-Length만 신뢰하지 않는다. 기존 OOXML 압축해제 120 MiB·ZIP 항목 5,000·압축비 250 제한을 임의 완화하지 않는다.

제품 초기 엔지니어링 기본안: 원천별 데이터 20,000행 이하, 선택 50열 이하, 선택 영역 셀 250,000개 이하, 키 최대 3열, 단일 필드 4,096자 이하, 출력 압축파일 20 MiB 이하. 모든 제한을 동시에 적용하므로 20,000행×50열이 허용된다는 뜻은 아니다. 기존 한도가 더 엄격하면 먼저 유지한다. 파싱/분석 job deadline은 30초를 시작값으로 검토하고 실제 상한 부하시험으로 결정한다. 숫자는 플랫폼의 허용량·성능 보증이 아니라 검증할 제품 기본안이다. 하나의 Settings/지원 화면에서 관리하며 출시 전 확정한다.

OOXML sparse/잘못된 dimension·XML 폭탄·외부 관계·CSV 폭넓은 행·과도한 필드를 처리하다 자원 제한에 닿으면 안전하게 전체 작업을 거부한다. 행 일부만 처리하고 유료 전체 보고서를 내지 않는다. 피벗·매크로·Power Query·외부 링크·수식을 실행하지 않는다.

## 2. 선택 영역·자료 의미

A/B 역할, 시트/표 범위, 헤더행, 거래번호/금액 열, 비교 기간 또는 기준시점, 금액 의미(공급가/총액 등), KRW·원 단위를 사용자가 확인한다. 값 예시로 추천할 수 있으나 정책 동의로 대신하지 않는다.

같은 행을 두 번 선택하거나 중복 헤더를 모호하게 매핑하지 않는다. 숨김/필터행은 묵시 제외하지 않으며 기본 포함 사실을 알린다. 별도 합계행은 자동 추정 삭제하지 않고 사용자가 명시 제외하거나 선택 범위를 조정한다. 영역 내 제외에는 source_row_id·사유를 남긴다. 표 밖 자료는 '미선택 영역'으로 구분한다. 제외/미선택을 비교 완료로 세지 않는다.

서로 다른 금액 의미·통화·집계단위·기간은 선결제 차단한다. 날짜가 키에 필요하면 텍스트 내보내기 및 동일 형식 확인을 안내하며 Excel serial-date를 몰래 업무날짜로 추정하지 않는다.

## 3. 식별자·금액 typing

키는 확인된 텍스트 1~3열의 tuple이다. `'01'`과 `'1'`, `'abc'`와 `'ABC'`, 앞뒤 공백이 다른 문자열을 기본적으로 다른 값으로 보존한다. 열을 `a|b`처럼 단순 이어붙여 복합키 충돌을 만들지 않는다. tuple 또는 길이 구분 직렬화로 hash한다. 빈 문자열/공백만 있는 키는 자료오류다.

Excel의 숫자형 식별자는 사용자 원형을 잃었을 수 있다. 첫 profile은 키를 텍스트로 요구하고 숫자키를 값내보내기/원본 확인으로 돌린다. 이미 손상된 긴 식별자나 표시 서식의 선행0을 복구했다고 주장하지 않는다. 임의 Unicode 정규화, 공백제거, fuzzy matching 없음.

금액은 유한한 정수 KRW로 정확히 읽는다. 실제 숫자형의 정수나 명시된 ASCII 정수 문자열을 지원하며, CSV의 적법한 3자리 쉼표 묶음은 검증 후 해석할 수 있다. bool·날짜·공란·NaN·Infinity·수식·과학 표기·소수는 초기 profile에서 미지원/자료오류로 분리한다. 음수와 0은 유효하다. `'0'`과 빈칸은 다르다. 값 문자열을 eval하지 않는다. 계산은 Python int/검증된 Decimal로 수행하고 API 금액은 정수 문자열로 보내 JS Number의 손실을 피한다.

선택한 키/금액에 Excel 수식 cell이 있으면 캐시가 있어도 preflight에서 차단한다. 수식이 아닌 명시적 문자열 `=1+1` 같은 키는 비신뢰 텍스트로 취급하고 실행하지 않는다. CSV/XLSX 출력 안전은 별도 적용한다. 수식을 계산하지 않는다는 사실은 공식 라이브러리 범위와도 일치한다. [S1](../research/TECHNICAL_SOURCES.md#s1)

## 4. 고정 입력 계약

각 row는 `source_id`, `source_version`, `source_row_id`, 사용자 결과에만 쓰는 원천 시트/행, `raw_key_parts`, `canonical_key`, 금액 원값/정수값 또는 오류 이유를 갖는다. 개인정보 최소화를 위해 미선택 열을 정규화 결과에 복제하지 않는다. 원천 파일 전체가 업로드됐다는 사실 자체는 숨기지 않는다.

`spec_hash`는 두 원천 hash + 선택 범위 + exclusion + mapping + 금액의미/기간/통화/오차정책 + profile/schema/engine version의 canonical 직렬화에 결합한다. 키나 raw content가 드러나는 hash 입력 원문을 로그에 남기지 않는다. request owner는 인증 서버에서 결정하며 클라이언트 owner_id를 신뢰하지 않는다.

## 5. 선결제 적합성

`NOT_ELIGIBLE`, `ELIGIBLE_WITH_LIMITATIONS`, `ELIGIBLE`을 사용한다. 안전/형식/필수 매핑·기준 불일치, 빈자료, 선택 수식, 양쪽 모두 유효한 공통 1:1 키가 하나도 없는 경우는 NOT_ELIGIBLE이다. 중복·오류 일부가 있어도 공통 유효쌍이 있으면 그 제한을 별도 확인한 후 ELIGIBLE_WITH_LIMITATIONS로 진행할 수 있다. 미리 비교를 했더라도 신규 유료 행별 결과와 차액 총계는 반환하지 않는다.

원본 미리보기·각 자료 중복/입력오류 위치·왜 지원 불가인지·확인해야 할 범위는 고객이 구매 여부를 판단할 수 있게 무료로 제공한다. 문제를 고치려면 결제해야만 하는 함정을 만들지 않는다. 새로운 실제 대사 결과 목록·행별 차액·보고서는 유료 사용권 뒤 제공한다.

## 6. 분류의 우선순위

키별 grouping 전에 금액이 나쁜 행을 삭제하지 않는다. 다음 순서로 **각 원천 행을 정확히 한 번** 배정한다.

1. 키 자체가 무효면 그 원천 행을 `INPUT_ERROR/INVALID_KEY`로 격리한다. 이 행의 알려진 금액도 전체 알려진 금액 합에는 보존한다.
2. 유효키별 양쪽 행을 모은다. 어느 쪽이든 2개 이상이면 **그 키의 양쪽 모든 행**을 `AMBIGUOUS/DUPLICATE_KEY` 한 그룹으로 보류한다. 나쁜 금액이 섞이면 하위 오류 이유도 보존한다. 임의 첫 행 선택·합산 매칭 금지.
3. 중복 없는 키에 나쁜 금액이 하나라도 있으면 반대쪽의 정상행도 함께 `INPUT_ERROR/INVALID_AMOUNT`로 묶는다. 잘못된 A금액을 지운 뒤 B를 ONLY_B로 만들지 않는다.
4. 양쪽 1행씩이고 금액도 유효하면 delta=A−B. abs(delta)≤확인된 오차이면 `MATCHED`, 초과이면 `AMOUNT_DIFF`. 오차 기본 0원. 오차 내 delta도 원값 그대로 보존한다.
5. 나머지 유효한 단독 키는 `ONLY_A`, `ONLY_B`. 반대 자료의 일부 키가 무효라는 제한도 전체 보고서에 남기며 '실제 누락 확정'이라고 하지 않는다.

한 결과 그룹이 여러 원천 행을 포함할 수 있다. **그룹 수 / A원천행 수 / B원천행 수 / 미상 금액 행 수**를 별도로 보여준다. UI에서 '8건'이라고 쓰면 8그룹인지 14원천행인지 명시한다.

## 7. 보존식·안전한 공개

선택 데이터행 수 = 결과에 배정된 행 수 + 명시 제외행 수(원천별). 한 row_id가 중복/누락되면 출력 불허. 결과 분류는 정렬과 무관하고 A/B를 바꾸면 ONLY_A/B가 교환되고 1:1 delta 부호가 반대여야 한다.

알려진 A금액합−알려진 B금액합 = 1:1 delta 합 + ONLY_A합−ONLY_B합 + 미비교 알려진 A합−미비교 알려진 B합.

미상 금액 행이 있으면 '전체 장부합' 대신 '알려진 금액 합'이라고 표시한다. 모호 그룹 합계는 참고용 합계이며 비교 성공/손실 합계가 아니다. 필터는 전체 summary와 CSV/XLSX 산출물의 범위를 바꾸지 않는다. 일부 계산/파일제한/검증 실패는 report READY를 막는다.

## 8. 개발 검증

`fixtures/BASELINE_EXPECTED.json`과 `fixtures/EDGE_CASES.json`의 고정 사례를 먼저 연결하고 생산 엔진을 실제 호출하는 테스트를 만든다. 패키지 validator의 성공을 제품 시험 성공으로 대체하지 않는다. 추가 독립 holdout·정상 예외·경계·resource 시험을 만든 뒤 정답을 고정한다. 기존 M4 waiver는 그대로 두고 이 상품의 새 예외를 사후 끼워 넣지 않는다.
